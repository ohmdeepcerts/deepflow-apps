# Migration history

These files are SQL Supabase has recorded as already applied to the live project (`dzqyqpuhxdrrpipbehpk`), pulled directly from `supabase_migrations.schema_migrations`/`apply_migration` and committed here. Before the first batch of these, this history existed only inside Supabase — this folder is the fix for that gap (`ARCHITECTURE_REDESIGN_PROPOSAL.md` §1.2/1.4, and roadmap item M5 in `docs/19_Future_Roadmap.md`).

**Every schema change from this point on should be written as a new, timestamped file here first, then applied** — so the repository and the live database never drift apart again.

## Standing up a fresh project? Read this first

Every file in this folder **except `0000_initial_schema.sql`** is an incremental change (`ALTER TABLE`, `CREATE INDEX`, `CREATE POLICY`, `CREATE OR REPLACE FUNCTION`, `DROP ...`) that assumes its target already exists. None of them contain a `CREATE TABLE`. Replaying this folder in order against a genuinely empty Supabase project fails immediately on the first statement — there's nothing yet to `ALTER`. This was a real, confirmed gap; see `docs/architecture/07-sql-migrations.md` §2 and §4, and `docs/planning/23-developer-onboarding.md` §B2, for the full writeup of how it was found.

`0000_initial_schema.sql` closes it. It's a from-scratch, earliest-timestamped baseline generated by introspecting the live project's catalog directly (`information_schema`, `pg_catalog`, `pg_proc`, `pg_policies`, etc.) — every table, constraint, index, function/RPC, the one trigger, every RLS policy, and the realtime publication membership, all in their current, final form as of 2026-08-11.

- **Standing up a brand-new, empty Supabase project at DeepFlow's current schema state?** Apply *only* `0000_initial_schema.sql`. Do not also replay the other timestamped files afterward — every change any of them ever made is already reflected in the baseline in its final form, so replaying them on top would re-attempt already-applied changes and fail (or in a few IF-NOT-EXISTS-guarded cases, silently no-op).
- **The rest of this folder — every `YYYYMMDDHHMMSS_*.sql` file — is this specific project's historical change log, not a second step of a bootstrap sequence.** It's kept for audit trail and so future changes have a consistent place to land, not because a fresh install needs to replay it.
- **Working against the existing live GB Electrical project?** You never need `0000_initial_schema.sql` at all — the schema it describes already exists there.
- `0000_initial_schema.sql` itself documents its own scope limits in its header comment (what it can't capture: the `auth` schema's own tables, Storage bucket/policy configuration, Edge Functions).
