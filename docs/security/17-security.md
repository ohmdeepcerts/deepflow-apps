# 17 — Security

DeepFlow's security posture and audit history: what controls exist today, why, and what's been found and fixed since the project's pre-migration baseline. This document does not track currently-open items — that's [18-known-issues.md](18-known-issues.md), a sibling document. It also doesn't re-derive the authentication/authorization mechanics ([08-authentication-and-roles.md](../architecture/08-authentication-and-roles.md)), the RLS/advisor inventory ([06-supabase.md](../architecture/06-supabase.md)), the Storage access mechanism ([09-storage.md](../architecture/09-storage.md)), or the escaping-helper inventory ([`docs/ui/16-ui-documentation.md`](../ui/16-ui-documentation.md)) — it links to each and summarizes only what's needed to tell the security story on its own.

**Methodology:** the three fixes this document opens with (§6, rows dated 2026-08-08) were each verified independently in this session — the migration files were read directly, the live function definitions were pulled from `pg_proc` via the Supabase MCP server against project `dzqyqpuhxdrrpipbehpk`, and `get_advisors` (security) was re-run live rather than trusted from an earlier pass. The historical record (§6, everything before 2026-08-08) comes from two sources: `docs/15_Security.md` — a dedicated security audit committed 2026-07-21 as a deliberate "baseline snapshot before architecture migration" (commit `3fe5b65`), describing the old flat-file apps (`index.html`, `engineer.html`, `client-portal.html`) before the Vite/ES-module rewrite — and `git log`, read for commit messages that name specific findings and fixes. Where a commit message is the only surviving detail (the SQL itself was applied live and never captured as a repo migration file — the same repo-vs-live gap [07-sql-migrations.md](../architecture/07-sql-migrations.md) documents in depth), that's stated plainly rather than reconstructed from guesswork.

## 1. Executive Summary

`docs/15_Security.md`'s 2026-07-21 baseline found a system that was, in its own words, wide open: anonymous Storage upload/list/delete, an anonymously-callable RPC exposing every staff email, every database table readable by anyone with the public anon key, and widespread unescaped HTML rendering. In the roughly two and a half weeks since (2026-07-21 to 2026-08-08, the full span of this repository's git history), each of those has been closed: RLS was tightened from a blanket "any authenticated user, ALL access" catch-all to 42 role-scoped policies across 20 tables (§3), the Storage bucket went from publicly readable-by-anyone to genuinely private with signed URLs and RLS-gated access on every read and write (§4), the highest-impact XSS breakout sites were fixed and a dead, unrate-limited PIN-brute-force RPC was revoked (§5), and this same session closed two further gaps found during the documentation pass itself — an RPC checking the wrong role, and a disaster-recovery trigger that referenced a dropped column (§6). What remains is tracked in [18-known-issues.md](18-known-issues.md): escaping is applied inconsistently rather than systematically (§5 below), most authorization is still a client-side UI concern with RLS as the real backstop rather than a second application-layer check (by design, not a gap — see [08-authentication-and-roles.md §1.4](../architecture/08-authentication-and-roles.md#14-role--writefield-permissions)), and leaked-password protection is unavailable on the project's current billing plan. For a single-tenant trade business running one production Supabase project with a small live user base, this is a reasonably secured system today — every data and file access path has a real, server-side, RLS- or RPC-enforced check behind it, not just a UI that declines to show a button.

## 2. Authentication & Authorization — Summary

Full detail lives in [08-authentication-and-roles.md](../architecture/08-authentication-and-roles.md); this is a one-paragraph orientation, not a duplicate. The three apps implement three genuinely different mechanisms sharing one `users` table: the Office App uses real Supabase Auth (email + password); the Engineer App uses a custom phone + 6-digit PIN verified server-side by a `SECURITY DEFINER` RPC with real bcrypt hashing (`pgcrypto`) and a 5-attempt/15-minute lockout; the Client Portal has no account at all — a URL parameter identifies the entity, with an optional 6-digit PIN (same bcrypt/lockout shape) as the only thing that survives a leaked link. Authorization above the database is role-and-permission-flag-based and enforced almost entirely in client JavaScript — by design, since the real boundary is RLS underneath it (§3) — with one deliberate server-side exception (`jobs_office_delete`, gated on `can_delete=true OR role IN ('admin','manager')` at the policy level, not just in the UI). [08-authentication-and-roles.md §5](../architecture/08-authentication-and-roles.md#5-known-gaps--observed-directly-not-inferred) itself documented two gaps found during that document's own review — an over-broad `get_auth_users()` role check and a disaster-recovery trigger referencing a dropped column — both of which were fixed in this same session; see §6 below for the verified evidence.

## 3. Row Level Security Posture

Full inventory — all 42 live policies, the five `SECURITY DEFINER` helper functions, the anon/authenticated RPC split — is in [06-supabase.md §3](../architecture/06-supabase.md#3-row-level-security). Summarized here, with the advisor snapshot re-confirmed live in this session (not carried over from when 06-supabase.md was written):

- **Coverage:** RLS is enabled on all 21 `public` tables, no exceptions. `push_subscriptions` has zero policies (deny-all by default) — dead schema for a not-yet-wired feature, not an oversight.
- **The historical `df_access` catch-all is confirmed gone.** This policy's own logic — "any authenticated user OR any valid engineer token gets `ALL` access" — made every more carefully scoped policy on the same table moot, since Postgres OR-combines permissive policies. A direct `pg_policies` query for `%df_access%` across `public` returns zero rows today.
- **Every current policy routes through one of five `STABLE SECURITY DEFINER` helper functions** (`is_office()`, `is_engineer()`, `is_valid_engineer_token()`, `my_engineer_name()`, `my_token_engineer_name()`) rather than inlining role logic per-policy — `STABLE` marking plus `(select auth.*())` initplan wrapping means these get evaluated once per query, not once per row.

**Security advisors, re-run live against `dzqyqpuhxdrrpipbehpk` in this session:**

| Category | Count | Level | Assessment |
|---|---|---|---|
| `rls_enabled_no_policy` | 1 (`push_subscriptions`) | INFO | By design — dead schema, no live writer, deny-all default is correct |
| `anon_security_definer_function_executable` | 22 | WARN | By design — the entire mechanism behind Engineer PIN login and Client Portal access, which have no RLS-checkable session of their own |
| `authenticated_security_definer_function_executable` | 33 | WARN | By design, same reasoning, for the authenticated-only subset (document-number generators, `get_auth_users`, PIN admin actions) |
| `auth_leaked_password_protection` | 1 | WARN | Known, accepted gap — a paid Supabase Auth add-on (HaveIBeenPwned checking) not available on the project's current plan tier |

**57 total lints, the same three-category shape [06-supabase.md](../architecture/06-supabase.md#4-live-security--performance-advisors) reported** — confirming the posture hasn't drifted across the several migrations that landed after that document was written. No `rls_disabled_in_public` finding, and no unrestricted-table finding, appeared in either run.

## 4. Storage Security

**What the exposure was.** The `deepflow` Storage bucket — the only bucket, holding every certificate PDF, invoice PDF, and job/engineer photo — was `public: true`. A public bucket in Supabase bypasses `storage.objects` RLS entirely for reads: any of the 7 RLS policies gating that table (`deepflow_staff_select`/`_insert`/`_update`/`_delete`, etc.) governed writes and authenticated reads, but the public URL form (`/object/public/deepflow/<path>`) served any file to anyone who had or could guess its path, with no auth check and no expiry, regardless of what those policies said. Every upload helper in all three apps returned exactly that public URL form after upload.

**What fixed it.** In this same session: the bucket was flipped to `public: false` (migration `20260808_make_deepflow_bucket_private.sql`), while it held zero objects (confirmed live — the 2026-08-06 production data reset had already cleared it, so no existing shared link was broken). All three apps were updated to resolve short-lived signed URLs instead of the now-dead public form:

- **Office and Engineer** — both hold a real session (Supabase Auth or the Engineer app's `x-engineer-token`), so both call `signedUrl()` themselves, authorized by `deepflow_staff_select`. 1-hour expiry for in-app viewing, a deliberate 10-year exception for links embedded in emailed certificates (so an old email's "Download Certificate" link doesn't die).
- **Client Portal** — has no session to sign a URL with, so a new Edge Function, **`portal-sign-url`**, bridges it: given the visitor's `(type, id)` plus the storage paths their own records reference, the function re-resolves that identity server-side (the same way `portal_get_jobs`/`portal_get_certs`/etc. already do) and signs a requested path only if it's genuinely found among that identity's own records — a guessed or adjacent path is silently dropped, never signed. 6-hour expiry.

**Residual risk, stated plainly rather than treated as new.** A signed URL is still a bearer credential for its validity window — someone who obtains a signed link (1–6 hours, or 10 years for emailed certs) can use it without further authentication until it expires. This is the normal, accepted trade-off of signed-URL access control, not a gap introduced by this fix; the alternative (no signed URLs at all) is what the public-bucket state already was, minus even the expiry. `get_advisors` (security) was re-run immediately after the bucket flip and returned no new finding.

Full mechanism — every policy, both helper-function checks, the exact expiry per app/use-case, and the delete-orphan caveat — is in [09-storage.md §3](../architecture/09-storage.md#3-access-control-private-bucket-signed-urls-one-edge-function-bridging-portals-missing-session); not duplicated here.

## 5. Input Handling / XSS Posture

**Historical baseline (2026-07-21, pre-migration flat-file apps):** `docs/15_Security.md` counted injection sites against escaping-call sites directly in the three then-monolithic HTML files — `index.html`: 326 `innerHTML` injection points against 10 escaping calls; `engineer.html`: 38 injection points, zero escaping mechanism defined anywhere in the file; `client-portal.html`: 55 escaping calls against 24 injection points (already the most disciplined of the three). Those counts describe files that no longer exist in that form — the codebase has since been split into `apps/office`, `apps/engineer`, `apps/portal` as ES modules — so they're historical context, not a current measurement.

**2026-07-25 fix (commit `044af4f`):** two confirmed attribute-context breakouts in the Portal (`properties.js`'s search box, an invoice-preview `data-id`, both using the narrow text-node escaper `escText` where attribute-safe `escAttr` was actually needed) and two `onclick="fn('${name}')"` handler breakouts in the Office App (`timesheets.js`, the WhatsApp panel in `main.js`) were fixed. The same commit fixed a concrete, non-theoretical bug in the same family — engineer names containing an apostrophe (O'Brien, O'Connor — ordinary UK surnames) broke those `onclick` handlers outright — and revoked `EXECUTE` on the dead `verify_engineer_login` RPC, which had no rate limiting or lockout and was reachable by `anon` directly via the REST API even after the app itself stopped calling it.

**Current state, per [`docs/ui/16-ui-documentation.md` §2.3](../ui/16-ui-documentation.md#23-where-interpolation-happens-without-escaping--verified-against-current-source)** (a sibling document that re-swept the current source specifically for this): escaping today is real but inconsistent, not systematic. `packages/ui/escaping.js` provides `escHtml`/`escAttr`/`escText`, used 124 times in `apps/office/main.js` and consistently across the Portal (44 call sites) — but the same file that escapes one field sometimes leaves an equivalent field raw (`apps/office/directory.js` escapes job-search results once and leaves `persons`/`agencies` name/notes fields unescaped everywhere else in the same file; `certs.js`'s Property-Cert-Dashboard rows escape `c.address` while the Certificates-tab rows three hundred lines later render the same field raw). Office's own `toast()` builds `innerHTML` from an unescaped message argument at real call sites carrying interpolated Directory data. None of this was fixed as part of writing that document — it's recorded as current, file:line-level fact for whoever picks up the next pass, per this repo's own stated preference for concrete evidence over an abstract "audit this." See [18-known-issues.md](18-known-issues.md) for whether it's tracked as an open item.
